# City Highways — сервер профилей (Supabase)

Проект Supabase: **cityhighways** (`nswqxnjyxlrtfzdlounk`, регион eu-central-1, Франкфурт).
Адрес: https://nswqxnjyxlrtfzdlounk.supabase.co

## Что где

| Часть | Файл | Что делает |
|---|---|---|
| Таблицы и права | `supabase/migrations/20261119_players_admin.sql` | `players` — профили, `admin_actions` — действия администратора, `admins` — кто администратор. RLS: анонимам ничего, администраторам — всё |
| Функция `player-sync` | `supabase/functions/player-sync/index.ts` | Принимает профиль из игры, проверяет билет Steam, сохраняет, отдаёт бан и действия |
| Админ-панель | `admin/index.html` | Список игроков, поиск, профиль, начисление и списание влияния, выдача и изъятие вещей, сообщения, бан, CSV |
| Клиент в игре | `Assets/CityHighways/Presentation/CloudProfiles.cs` | Синхронизация при запуске, после изменений и раз в 5 минут |

**ID игрока** — `steam:<SteamID64>`: тот же SteamID, что у его профиля Steam. Он показан в профиле в игре, по нему
игрок ищется в админ-панели. Epic подключится так же (`epic:<ID>`), когда будет EOS SDK.

## Настроить один раз

1. **Секреты функции** (Supabase → Edge Functions → Secrets):
   - `STEAM_WEB_API_KEY` — издательский ключ Web API (Steamworks → Users & Permissions → Manage Groups → Web API Key);
   - `STEAM_APP_ID` — AppID игры.

   Пока ключей нет (тестовый AppID 480), можно временно поставить `ALLOW_UNVERIFIED=1`. Тогда SteamID берётся из
   запроса без проверки, и запись помечается «без проверки». **Перед релизом этот секрет нужно удалить.**
2. **Учётная запись администратора.**
   - Supabase → Authentication → Users → **Add user** (почта и пароль, подтверждение не нужно).
   - Затем в SQL Editor выполнить:
     ```sql
     insert into public.admins (user_id) select id from auth.users where email = 'ВАША_ПОЧТА';
     ```
   - Authentication → Sign In / Providers: **выключить «Allow new users to sign up»**, чтобы никто
     не мог создать себе учётную запись.
3. **Админ-панель.** Открыть `Server/admin/index.html` в браузере (можно прямо из папки) и войти.

## Как работает синхронизация

1. Игра получает у Steam билет `GetAuthTicketForWebApi("cityhighways")` и отправляет его вместе с профилем.
2. Сервер проверяет билет у Steam (`ISteamUserAuth/AuthenticateUserTicket`): так он узнаёт SteamID, и выдать
   себя за другого игрока нельзя.
3. Профиль сохраняется в `players`. Бан и причину меняет только администратор, игра их не перезаписывает.
4. В ответ приходят неприменённые действия администратора. Игра применяет их (влияние, вещи, сообщения) и в
   следующем запросе сообщает номера применённых. Применённое повторно не срабатывает.
5. Кошелёк и вещи в таблице — копия из игры. Менять их нужно **действиями** (кнопки в панели), а не правкой
   таблицы: прямую правку игра перезапишет при следующей синхронизации.

Публичный ключ (`sb_publishable_…`) в игре и в панели — не секрет: таблицы закрыты RLS, игра пишет только через
функцию, а панель видит данные только после входа администратора.

## Социальная часть: рекорды, повторы, клубы (функция `social`)

| Часть | Файл | Что делает |
|---|---|---|
| Таблицы | `supabase/migrations/20261120_social_records_clubs.sql` | `records` — лучший результат игрока на карте в режиме вместе с повтором; `clubs`, `club_members`, `club_weeks` (цель недели), `club_contrib` (вклад участников), `club_logos` (заработанные логотипы); функция `club_contribute` — атомарный вклад |
| Функция `social` | `supabase/functions/social/index.ts` | Тот же вход по билету Steam. Действия: `report`, `friends`, `replay`, `club`, `club_list`, `club_create`, `club_join`, `club_leave`, `club_logo`, `club_open` |
| Клиент | `Presentation/SocialCloud.cs`, `Ghosts.cs`, `Replays.cs`, `MenuClubPage.cs` | Рекорды друзей, рейды, повторы, страница «Клубы и друзья» |

Миграция применена и функция задеплоена (20.11.2026, `verify_jwt = false`, как у `player-sync`: функция сама проверяет билет Steam).
Секреты — те же, что у `player-sync`.

- **Рекорды.** После партии соревнования или кооператива игра отправляет счёт и повтор (JSON → gzip → base64, ~20–40 КБ).
  Запись обновляется, только если счёт лучше прежнего. Друзей сервер не знает: игра присылает SteamID друзей из клиента
  Steam, сервер отдаёт их рекорды.
- **Цель недели** (ISO-неделя, конец — понедельник 00:00 UTC) одна на все клубы и меняется по кругу:
  - км дорог — 250 на участника (участок = 10 км);
  - контракты — 5 на участника;
  - заказы города — 3 на участника;
  - победы — 2 на участника;
  - грузы в магнате — 15 на участника.

  Участников считается не меньше четырёх. Цель (и её размер) фиксируется при первом вкладе за неделю.
- **Логотип** — строка `форма.знак.цвет.ранг` (рисует `ClubLogo` в игре). Стартовые — ранг 0. За выполненную цель
  клуб получает логотип, собранный из хеша «id клуба / неделя»: он уникален, ранг 1–3 растёт с числом выполненных недель.
  Владелец выбирает герб; он виден в лобби сетевой игры рядом с именами участников.
- **Ограничения от накрутки** (клиенту доверяем, как и с профилем): за партию в цель засчитывается не больше
  60 участков, 20 контрактов, 15 заказов, 80 грузов. Счёт — от −100 до 1000. Если понадобится строже, повтор можно
  переиграть на сервере — партия детерминирована.
- Таблицы закрыты RLS. Администраторам открыто чтение: в админ-панели их пока нет, но их видно в SQL Editor.

## Персональные данные

На сервере хранятся SteamID, ник и игровые данные — это персональные данные. Для страниц игры в Steam и EGS
понадобится политика конфиденциальности. Для игроков из России есть требования о локализации данных граждан РФ
(152-ФЗ). Проект сейчас во Франкфурте. Перед релизом стоит уточнить это у юриста.

## Этап 3 — первичная проверка отчётов и повторов (задача №19)

Код в ветке с данной доработкой **не развёрнут в Supabase автоматически**.
Для применения нужно проверить новый `social` Edge Function в тестовом
окружении и отдельно выполнить его деплой. Запуск только Unity CI недостаточен.

Сервер теперь перед сохранением результата режима `classic`/`coop`:
- Проверяет точные типы, границы очков, места за столом, seed и названия карты.
  Значения очков больше **не обрезаются** до допустимого диапазона.
- Принимает только gzip/base64-повтор размера до 700 КиБ и распаковывает
  его с ограничением в **4 МиБ**, чтобы сжатые «бомбы» не занимали память.
- Проверяет версию повтора, режим, карту, seed, автора-человека, его место
  за столом, счёт, исход, списки игроков и ограниченный список команд.
  Несогласованные поля отклоняются **до записи рекорда и вклада в клуб**.
- Больше не обрезает текст base64 при сохранении: сохраняет ровно тот
  архив, который прошёл проверки.
- Читает HTTP-тело по частям и отклоняет запросы свыше **768 КиБ**
  до сборки полного текста, в том числе без заголовка Content-Length.
  Проверяет корректность UTF-8.
- Не затрагивает способ входа по билету Steam и обязательную
  предварительную запись игрока в таблице `players`.
- Оставляет `magnate` без повтора, как в действующем клиенте:
  этот режим требует отдельной проверки результатов/клубного вклада.

**Граница защиты:** это проверка *согласованности клиентского повтора*,
а не доказательство честного счёта. Злоумышленник может изменить
`authorScore`, `scores` и прочие поля повторов согласованно. Для
авторитетной проверки необходимо детерминированно воспроизвести
`GameStartInfo + GameCommand[]` на доверенном серверном движке,
пересчитать очки и сравнить результат. Пока это не реализовано,
рекорды нельзя называть «проверенными сервером». Аналогично
идемпотентность недельных вкладов, защита от повторных запросов и
проверка `magnate` остаются отдельными задачами этапа 3.

### Запуск локальных тестов (не требует Steam SDK / Supabase)

```bash
node --test Server/supabase/functions/social/*.test.mjs
```

Workflow `.github/workflows/social-replay-validation.yml` запускает эти
тесты при изменениях функции и контролирует подключение валидатора
к обработчику `report`. CI не выполняет миграции/деплой Supabase.

### Ручной приёмочный сценарий после деплоя в staging

1. С реальным тестовым Steam-билетом и заранее синхронизированным
   профилем отправить обычную завершённую Classic/Coop партию.
2. Проверить запись рекорда, скачивание и воспроизведение повтора,
   обновление личного рекорда только при улучшении.
3. Повторить запрос с подменённым `score`, `won`, `seed`,
   `mapPath` или `authorSeat`. Ожидается 400 и **отсутствие**
   изменений рекорда и клубного вклада.
4. Отправить повреждённый base64/gzip и архив с распаковкой свыше
   4 МиБ: запрос отклоняется без исчерпания памяти.
5. Протестировать HTTP-тело больше 768 КиБ с Content-Length
   и без него; сервер должен ответить 413.
6. Проверить старые сохранённые рекорды, журналы, клубы и `magnate`
   на совместимость — правок схемы БД на этом этапе нет.
7. Проверить запрет записи для неавторизованного/заблокированного
   Steam-профиля и работу без Steam в локальной игре.

## Этап 3 — идемпотентные клубные отчёты и конкурентные рекорды

Предыдущая проверка `report-validator.mjs` отбрасывает повреждённые
или внутренне несогласованные повторы, но **повторный POST** всё ещё
мог несколько раз увеличить счётчик клуба. Кроме того, два одновременно
завершившихся POST могли перезаписать лучший результат худшим из-за
схемы `SELECT → UPSERT`.

### Новая миграция (обязательна перед деплоем функции)

`Server/supabase/migrations/20261125_idempotent_social_records.sql`

- `record_upsert_best` выполняет **один атомарный**
  `INSERT ... ON CONFLICT ... DO UPDATE WHERE excluded.score > records.score`.
  Он возвращает `{improved, best}`, включая случай равного результата;
  победный повтор не заменяется при меньшем/равном счёте.
- `club_report_receipts` хранит уникальную пару
  `(player_id, submission_hash)`. Исторические квитанции сохраняются
  при выходе из клуба или его удалении, но удаляются вместе с игроком.
  Включён RLS; доступ к записи — только через service_role RPC.
- `club_contribute_once` в **одной транзакции** вставляет новую
  квитанцию и вызывает существующий `club_contribute`. Конфликт
  по ключу возвращает `{accepted:false,closed:false}` без повторного
  увеличения суммы, счётчика игр и без нового логотипа. Если RPC
  не завершился, квитанция тоже откатывается.
- Перед транзакцией ещё раз проверяется принадлежность игрока клубу,
  чтобы устаревший запрос не мог начислить вклад покинутому клубу.
- Оба RPC доступны только для `service_role`; игроки не могут
  напрямую вызывать их через публичный Supabase API.

### Что считается одной партией

После разархивирования и проверки повтора сервер вычисляет
`SHA-256` по детерминированным данным: **режим, путь карты,
GameStartInfo и последовательность GameCommand**.
Ключи объектов упорядочиваются, поэтому другой порядок JSON-полей,
повторное gzip-сжатие, новый локальный ID/дата, ник и исправленный
отображаемый счёт не превращают ту же самую партию в новую.
Другая карта, seed, настройка партии или последовательность ходов
создают новый отпечаток.

Применяется пока **только к Classic/Coop**. Режим «Магнат»
сохраняет прежний `club_contribute`, потому что его
`ReportMagnate` не содержит сохранённого идентификатора игры.
Для него нужна отдельная модель стабильного run ID.

**Ограничение безопасности:** отпечаток защищает от случайных дублей,
повторной доставки запроса и идентичных повторов, но не от
мотивированного злоумышленника: поддельную историю команд можно
изменить и получить новый отпечаток. Точно так же первый отчёт
может содержать поддельные, но согласованные числа. Только
независимое воспроизведение движком на доверенном сервере с
проверкой игровых правил позволит назвать счёт защищённым от читов.

### Порядок развёртывания

1. Запустить существующие тесты и новый Node-suite:
   `node --test Server/supabase/functions/social/*.test.mjs`.
2. **Сначала** выполнить миграцию в staging Supabase.
   Проверить наличие `record_upsert_best`,
   `club_contribute_once` и таблицы `club_report_receipts`;
   проверить grants/RLS.
3. **Затем** развернуть новую Edge Function `social` в staging.
   На действующей функции до деплоя ничего не меняется.
4. Провести двухпоточное тестирование лучшего результата: низкий
   результат не должен перезаписывать высокий, независимо от порядка
   запросов.
5. Отправить один и тот же Classic/Coop replay 2–3 раза, в том числе
   с другой датой и ID файла: первый отчёт учитывается, дубли
   возвращают `club.amount=0`. Проверить итог `club_weeks.progress`
   и `club_contrib.games`, получение герба ровно один раз.
6. Проверить повторный запрос после выхода из клуба, после его
   удаления и после нового вступления: исторический replay
   не должен засчитываться повторно.
7. Протестировать `magnate` как регрессию; его дедупликация
   остаётся отдельной задачей.
8. После staging-верификации отдельно перенести **сначала
   миграцию, затем код** в production Supabase. Проверьте
   существующие данные до переключения (исторические дубли
   задним числом не исправляются).

### Автоматическая проверка

`.github/workflows/social-replay-validation.yml` запускает
Node-тесты при изменении нового SQL-файла или Edge Function.
Проверки подтверждают JS-контракт, формат отпечатка, сценарии
дублей и статические ключевые свойства SQL. Они **не запускают
настоящую PostgreSQL-транзакцию**, Supabase или игру.
Поведение под конкурентными запросами нужно проверить на staging
Postgres до включения в production.

## Этап 3 — защита от повторной отправки партии «Логистического магната»

В дополнение к защитным механизмам для Classic/Coop режим «Магнат»
передаёт в `social.report` отдельный **runId** — случайный GUID
(32 шестнадцатеричных символа в нижнем регистре, без дефисов).

- `LogisticsGame.ReportRunId` формируется единожды при создании
  `LogisticsGame` с помощью `Guid.NewGuid()`; он не зависит от
  seed процедурного города и сохраняется до конца жизни объекта партии.
  Повторный вызов `SocialCloud.ReportMagnate` для той же партии
  передаст тот же ID; новая партия получит другой.
- Unity-клиент отправляет отчёт только при `GameOver`, с
  человеческого места за столом; обучение/тренировку, как и раньше,
  исключает вызывающий `MagnateView.ShowResults`.
- Сервер проверяет тип и формат ID, обязательный `mapName`,
  целочисленный `score`, `won`, `stats.delivered` и
  согласованность `stats.won` с общим результатом. Все ошибки
  отклоняются **до** записи клубного вклада.
- Отпечаток `SHA-256("magnate/v1/" + runId)` вычисляется
  сервером. Игрок не присылает готовый hash. Отпечаток
  независим от заявленных счёта и статистики, чтобы
  исправленные поля при повторной отправке не создавали
  дополнительное начисление.
- «Магнат» теперь вызывает `club_contribute_once` из миграции
  `20261125_idempotent_social_records.sql` — уже
  существующий механизм атомарного зачёта одной партии.
  Повторный запрос возвращает `club.amount=0`, без новой
  квитанции, счётчика игр, недельного прогресса или логотипа.
- Отдельного серверного рекорда Магната в `records` по-прежнему
  нет. Схема таблиц не меняется. Режимы Classic/Coop и загрузка
  их повторов не изменены.

**Граница защиты:** runId создаётся на клиенте, следовательно
злоумышленник может его подменить и выдать другую партию за новую.
Это защита от ретраев и повторной доставки *того же ID*, не
античит и не проверка честности доставок/победы. Нужны
серверный учёт сессий и независимая проверка результатов.

**Совместимость:** новый сервер отклоняет отчёты Магната от
старых клиентов без runId. **Сначала** примените
SQL-миграцию из PR #97, **затем** проверьте новый клиент и
серверную функцию в staging и лишь после этого обновляйте
производственное окружение. Сам GitHub PR ничего не
развёртывает в Supabase. Сосуществование старых и новых
версий клиента нужно учесть в плане релиза; откладывание
серверного переключения или отдельный переходный режим
обсуждаются отдельно.

### Приёмочные тесты в staging

1. Запустить `node --test Server/supabase/functions/social/*.test.mjs`
   и все Unity Edit Mode тесты, затем собрать Unity-клиент.
2. Завершить настоящую партию Магната и проверить запрос
   `mode=magnate` с `runId` и корректными `stats.delivered/won`.
3. Отправить **точно тот же HTTP POST** повторно: первый
   увеличивает `club_contrib.games` и `club_weeks.progress`,
   второй возвращает `club.amount=0`.
4. Изменить счёт, имя города, доставленные грузы или флаг победы,
   сохранив тот же runId: повторно зачесть вклад нельзя.
   Несогласованность `won` и `stats.won` отклоняется.
5. Начать новую партию на таком же seed: с другим runId
   её отчёт должен быть отдельным. Старый отчёт не должен
   зачесться после выхода из клуба и повторного вступления.
6. Проверить отсутствие внесения изменений в таблицу
   `records` от Магната, скачивание повторов Classic/Coop
   и штатное начисление прогресса их клубных целей.
7. Протестировать старую сборку Магната: ожидается
   отклонение отчёта без ID, чтобы это не стало
   неожиданностью для пользователей при релизе.

**Тесты CI проверяют JS-контракт, тесты ID и связность
исходников, но не выполняют реальные PostgreSQL-транзакции.**
Проверка конкурентных запросов требует staging Supabase.

## Этап 3 — локальная очередь доставки отчётов (Unity)

После введения серверных квитанций и идемпотентности результатов
`SocialCloud` сохраняет отчёт партии **до** попытки отправки. При
отсутствии связи, неподтверждённом облачном профиле, таймауте
или 5xx результат не теряется при закрытии игры.

- `Presentation/SocialReportOutbox.cs` — дисковый журнал с ограничением
  **24 отчёта** и **740 КиБ на сериализованный запрос**. Данные лежат
  в `Application.persistentDataPath/social/pending-reports.json`,
  запись через временный файл и резервную копию `.bak`.
- Каждая запись хранит SteamID владельца, локальный ключ партии,
  JSON результата, количество попыток и UTC-время следующей отправки.
  **Ни Steam-ticket, ни пароль не пишутся в очередь**. Новый ticket
  запрашивается непосредственно перед каждым запросом.
- Результат Classic/Coop связывается с ID сохранённого replay;
  результат «Магната» — с ранее введённым `ReportRunId`.
  Повторный вызов в рамках партии не создаёт вторую локальную запись.
  Серверный `club_contribute_once` дополнительно обеспечивает
  идемпотентность в PostgreSQL.
- Отправка выполняется из существующего `SocialCloud.Tick()`
  после восстановления Steam и синхронизации профиля. Одновременно
  отправляется максимум один накопленный отчёт. При ошибке запись
  остаётся на диске, а повторная попытка откладывается
  (15, 30, 60… до 900 секунд; для постоянных/авторизационных
  ошибок — длиннее). Записи удаляются **только после успешного
  ответа сервера**.
- Отчёты строго привязаны к SteamID, под которым завершена партия.
  После смены аккаунта чужая очередь не отправляется; проверка
  выполняется также после асинхронного получения билета Steam.
  На странице «Клубы и друзья» число ожидающих отчётов показано
  только для текущего SteamID, на русском и английском.
- Цель недели заканчивается в **понедельник 00:00 UTC**. При
  запоздалой отправке за другую неделю клиент добавляет
  `skipClub=true`: сервер всё ещё может принять личный рекорд
  Classic/Coop, **но не увеличивает цель следующей недели**.
  Магнат не хранит личный рекорд, поэтому такой поздний отчёт
  только подтверждается, не начисляя прогресс.
  Это сознательно ограничивает зачёт после простоя/отключения.
  Границы недели вычисляются из локальных UTC-часов клиента;
  они **не являются доверенным античит-источником**.

### Ограничения и конфиденциальность

- Очередь может содержать ники игроков, игровую историю и данные
  карты; хранится **локально без шифрования**. Её удаление
  пользователем удалит ещё не доставленные результаты.
  При заполнении/недоступности диска игра покажет предупреждение,
  а не будет бесконтрольно создавать гигабайты файлов.
- Если SteamID не известен (игра запущена без Steam),
  результат в серверную очередь не добавляется. Локальная
  статистика игры от этого не зависит.
- Ошибки формата и несовместимости версий не удаляются молча:
  отчёт хранится с длительным backoff. После исправления сервера
  он может отправиться позднее, если текущий SteamID совпадает.
- Серверный код `skipClub` — **добровольный отказ** от клубного
  начисления; злонамеренный клиент не может с его помощью
  получить больше баллов. Достоверность времени завершения
  партии сервером пока не проверяется.
- Релиз по-прежнему требует миграцию из PR #97, новый server
  `social` из PR #98 и текущие Unity + Edge изменения.
  Никакие SQL-миграции или Edge Functions в Supabase через PR
  автоматически **не развёртываются**.

### Защита очереди от ошибок записи и повторных HTTP-запросов

- Операции добавления, удаления после ACK и изменения времени повторной
  попытки теперь **откатывают изменения в памяти**, если сохранение на диск
  не удалось. Неуспешный Enqueue больше не считается успешной очередью.
- После восстановления из .bak следующая запись **не заменяет исправный
  backup повреждённым основным файлом**. Отдельно проверяется фактический
  размер UTF-8 сериализованного файла, а не только JSON каждой игры.
- Если сервер уже принял отчёт, но удаление из локального файла не удалось,
  клиент держит ACK **только в памяти** и пытается сохранить удаление
  каждые 30 секунд, не отправляя снова HTTP. После перезапуска эта память
  теряется: старый отчёт может быть отправлен повторно, поэтому
  серверные idempotency receipts из PR #97–98 по-прежнему обязательны.
- При сбое сохранения времени повторной попытки (например, заполнен диск)
  действует локальный интервал в 30 секунд. Это предотвращает поток
  повторных запросов каждый кадр Unity.
- Пустой или некорректный ответ сервера не подтверждает доставку:
  отчёт остаётся в очереди и переносится на следующую попытку.
  Начиная с PR #101 поля ответа HTTP 200 проверяются до ACK; контракт
  требует фактической проверки на Steam/Supabase staging.
- Новые 5 NUnit Edit Mode тестов проверяют отказ записи,
  откат операций, две последовательные порчи основного файла и
  некорректные значения времени. Пять Node wiring-тестов фиксируют
  наличие защит в коде клиента. Node wiring **не подменяет** реальные
  тесты Unity и файловой системы.

**Ручная приёмка:** временно сделать очередь недоступной для записи во
время приёма ответа от Supabase; убедиться, что нет шквала запросов и
отчёт не исчезает. Вернуть запись, проверить локальное удаление без
нового HTTP. Повторить с порчей pending-reports.json при исправном
.bak и сменой Steam-аккаунта. Не считать этот пакет готовым к
релизу без Steam/Supabase staging и проверки точного SHA Unity CI.
Ни миграций, ни автоматического деплоя Supabase в пакете нет.


### Проверка подтверждения доставки социального отчёта (этап 3)

HTTP 200 **не является достаточным подтверждением**, если JSON ответа
имеет отсутствующие или некорректные поля. До удаления отчёта из
постоянной очереди клиент проверяет текущий контракт `social.report`:
`improved` — boolean, `best` — целое число от -100 до 1000,
`club` — null или объект со строковым `kind`, целочисленным `amount`,
boolean `closed` и `logo` (null или строка). Валидация выполняется
непосредственно в пути транспортного `Send<ReportResponse>`;
обычный `JsonUtility` сам по себе не различает отсутствующий boolean
и ответ false. Размер ответа ограничен 16 KiB символов.

Ошибочные, частичные, вложенно подделанные, дублирующие поля или
неожиданно большие ответы **не приводят к ACK**. Очередь сохраняет
отчёт и повторяет попытку по существующему backoff. Отправка
повторного POST после потерянного подтверждения безопасна в рамках
серверной идемпотентности из PR #97–98, но не доказывает честность
клиентского результата.

Уведомление об успехе не показывается, если SteamID сменился
после отправки запроса, но до получения HTTP-ответа. Подтверждённый
отчёт исходного пользователя всё равно удаляется из локальной очереди.
Данных других аккаунтов этот UI-обработчик не показывает.

**Совместимость:** Edge Function уже возвращает поля `improved`,
`best`, `club` во всех успешных ответах `report`; ни миграции, ни
автоматический деплой Supabase не требуются. Если в продакшне
работает другая версия функции, сначала проверить её контракт
на staging. Требуются Unity Edit Mode и Node wiring тесты на SHA
нового PR; не считать статические проверки заменой реального
Steam/Supabase тестирования.

**Ручная проверка:** ответ 200 с `{}` или неполным JSON не должен
удалять запись; корректный ответ с `club: null` либо с полной
структурой вклада должен приводить к ACK. Проверить смену Steam
аккаунта во время HTTP-запроса и убедиться, что уведомление старого
игрока не появляется у нового пользователя.


### Контроль целостности очереди и восстановление повреждённых файлов (этап 3)

Новый файл `social/pending-reports.json` сохраняет `formatVersion: 1`
и SHA-256 контрольную сумму канонического списка `entries`. Сумма
предназначена для обнаружения случайной порчи файла, **не** для проверки
подлинности игры, SteamID, рекорда или защиты от читов. Старые файлы
`{"entries":[...]}` читаются без миграции, если имеют точный сериализованный
формат старого клиента; при следующей записи обновляются до нового формата.

- Основной файл используется только если валидны **все** записи и
  контрольная сумма; частичная загрузка со скрытым выбрасыванием записей
  запрещена. При невалидном файле проверяется `.bak`.
- Если оба файла повреждены или имеют неподдерживаемый формат, новые
  записи **не пишутся поверх них**: `LoadBlocked` останавливает запись,
  исходные байты сохраняются для восстановления. В интерфейсе при попытке
  добавить отчёт показывается отдельное RU/EN предупреждение.
- Запрос с повреждённым локальным `requestJson` не удаляется. Он
  откладывается на час (эквивалент HTTP 422); другие отчёты того же
  Steam-аккаунта могут быть отправлены. Повторная попытка без
  восстановления данных снова будет отложена. Ошибка отсутствующей
  Steam-идентичности также явно показывается пользователю.
- Список ограничен 24 записями и ~18 МБ. Постоянно повреждённый
  отчёт занимает слот: перед ручным восстановлением следует сохранить
  копию `pending-reports.json` и `.bak`, не редактировать их во время
  работы игры. Здесь нет автоматического удаления или безопасного
  редактора очереди.

**Проверки:** Unity Edit Mode тесты на контрольную сумму,
восстановление из backup, legacy-миграцию, неподдерживаемую схему,
отказ перезаписи и fairness повторов; Node-тесты проверяют wiring.
Ни изменение Supabase, ни его автоматический деплой не выполняются.
Ручная staging-проверка и CI на точном SHA необходимы перед релизом.


### Изоляция социального состояния при переключении Steam-аккаунта (этап 3)

Состояние друзей/клуба, обновления профиля и сетевые callback теперь
привязаны к **SteamID и номеру сеанса**. Сценарий A → B → A не должен
повторно активировать ответ, запрошенный во время первого сеанса A.

- `CloudProfiles` сбрасывает `ServerId`, сетевую занятость и
  сообщения администратора при исчезновении или изменении SteamID.
  Ответ `player-sync` применяется лишь если его `id` равно
  `steam:<текущий SteamID>`, `platformUserId` совпадает со SteamID,
  и callback относится к текущему поколению сеанса. Запоздавшие ответы
  не переносят административные изменения и состояние профиля в
  новый сеанс.
- `SocialCloud.Available` требует, чтобы `ServerId` точно совпадал
  с текущим SteamID, а не просто был непустым. После входа под новым
  аккаунтом его социальные запросы не начинаются до собственной
  синхронизации профиля.
- При смене владельца сбрасываются `FriendRecords`, `Club`,
  `News`, ошибки, индикаторы загрузки, а обновления данных
  запрашиваются заново. Сетевые ответы прежнего поколения отклоняются
  и не изменяют новый интерфейс.
- Для исходящего отчёта с отменённым callback вызывается существующая
  обработка ошибки: запись остаётся в очереди и повторяется с backoff
  под исходным SteamID. Идемпотентность сервера сохраняет возможность
  безопасной повторной отправки, если первый POST всё-таки дошёл.
- Повторы друзей/клуба, созданные в старом сеансе, не могут
  использовать закэшированный `Replay` после входа в другой аккаунт.
  Страница клуба очищает поиск, приглашение и сохранённые результаты
  при смене идентификатора/поколения сеанса. Локальные повторы не
  блокируются ограничением на облачные данные.
- Накопленные отчёты на диске **не удаляются при смене аккаунта**:
  каждый остаётся привязан к владельцу и может повторно отправиться
  только после возвращения исходного Steam-пользователя.

**Проверки:** восемь NUnit-тестов `SocialAccountScopeTests` покрывают
смену владельца, отключение Steam, неверные идентификаторы и A → B → A;
десять Node wiring-тестов проверяют связи между облачной
синхронизацией, сетевым транспортом, страницей клуба и повторами.
Дополнительно обязательны Unity Edit Mode и Node CI **на head SHA PR**.

**Ручная проверка:** войти под Steam A (дождаться друзей/клуба);
сменить на B во время получения билета Steam и во время HTTP-запроса;
убедиться, что ни рекорды друзей, ни код приглашения, ни сообщения A
не видны у B. Дождаться отдельного sync B и проверить актуальные
данные. Вернуться к A: старые отложенные ответы первого сеанса A
не должны обновить UI, но его отчёты могут продолжить отправку.

**Границы:** проверки в этом PR не доказывают честность игрового
результата и не заменяют Steam/Supabase staging. Деплоя Edge Functions
или изменений SQL в пакете нет.


### Порядок ответов социальных запросов и изменения клуба (этап 3)

`SocialCloud` теперь использует независимые поколения запросов
`SocialRequestGate` для списка друзей и состояния клуба. Результат
старого GET **не должен перезаписывать** результат более нового
запроса и не должен сбрасывать флаг занятости нового запроса.
Смена Steam-аккаунта отменяет оба поколения, не затрагивая
сохранённую на диске очередь отчётов партий.

- `RefreshFriends`: повторное ручное обновление делает старый запрос
  устаревшим; при пустом списке друзей старая выборка сразу очищается,
  а запоздавший HTTP-ответ игнорируется. Ответ HTTP 200 без массива
  `records` **не** трактуется как корректный пустой список и не
  затирает последние успешные результаты.
- `RefreshClub`: результаты старых обновлений не заменяют новые,
  а десериализованный `null` не затирает имеющееся состояние
  клуба. Сетевые ошибки сохраняют последнее корректное состояние.
  С PR #105 все успешные ответы `club` проходят проверку
  полей до вызова `JsonUtility`; пустой JSON `{}` не заменяет клуб.
  `{"club":null}` сохраняется именно как отсутствие клуба.
- `ClubAction`: создание, вступление, выход, смена герба и открытости
  клуба выполняются последовательно — повторное изменение, пока
  прежнее не завершилось, отклоняется с локализованным сообщением.
  Новое изменение инвалидирует ранее начатые GET-запросы.
  Периодическая загрузка приостанавливается на время изменения.
  После неопределённого результата или ошибки инициируется
  свежий GET, чтобы согласовать отображение с сервером.
- Поиск открытых клубов использует отдельный номер запроса страницы
  и поколение Steam-сеанса. Запоздавшие результаты старой строки
  поиска или старого пользователя отбрасываются. Последние
  корректные результаты не исчезают при временной ошибке.
  Неполный JSON с отсутствующим `clubs` не считается успешным
  пустым поиском; список ограничен максимум 30 карточками.

**Тесты:** восемь Unity Edit Mode-тестов `SocialRequestGateTests`
проверяют независимость запросов, приоритет новых ответов, сброс
при смене владельца и блокировку старых колбэков. Тринадцать
Node-тестов проверяют интеграцию с фоновым обновлением, поиском,
клубными изменениями и локализацией ошибок.

**Staging-проверка:** искусственно задержать первый из двух GET
друзей/клуба, дождаться второго и выпустить первый — интерфейс

### Строгая проверка успешных ответов социального API (этап 3)

`SocialReadContracts` переиспользует существующий ограниченный JSON-парсер
`SocialReportAck` и проверяет типы и обязательные поля успешных ответов
до вызова `JsonUtility`. Не требуется менять формат Supabase Edge
Function: сервер уже отправляет `{"records":[...]}`, `{"club":null}`,
подробное состояние участника клуба или `{"clubs":[...]}`.

- Друзья: до 200 записей; у каждой проверяются `id`, Steam `playerId`,
  `mode`, `mapPath`, `mapName`, `score`, `won`, `seats`,
  `name`, `date`. Пустой массив допустим; отсутствующий `records`,
  незавершённые/неверно типизированные записи и повтор ключей — нет.
- Свой клуб: отсутствие членства представляется `{"club":null}`,
  а не пустым объектом `ClubInfo` (Unity иногда материализует его для
  JSON null). При наличии клуба обязательны сведения о владельце,
  коде приглашения, членах, неделе, достижениях, логотипах и максимум
  40 рекордах; вложенные массивы и числа проверяются по схеме.
- Поиск клубов: обязателен массив `clubs` максимум из 30 записей
  с корректными `id`, `name`, `tag`, `logo`, `members`.
  Некорректный элемент отклоняет **весь** ответ, а не исчезает
  бесследно из списка после десериализации.
- Ответ ограничен **256 KiB символов**, глубина вложений — 12,
  максимум элементов в JSON-контейнере — 256. Проверка не
  использует поиск подстрок и не принимает повторяющиеся JSON-ключи.
- При провале валидации вызывается обычный `failed` callback:
  ранее загруженные данные друзей/клуба сохраняются, а мутации
  клуба переходят в режим повторной проверки состояния.
  `social.report` продолжает отдельную обязательную ACK-валидацию,
  **без удаления из дисковой очереди** по неполному HTTP 200.

**Автоматическая проверка:** новый набор NUnit `SocialReadContractsTests`
