# Этап 1.5 — Unity scenes and maintainable assets

## Audit of `main` (2026-11-22)

- Unity version: **6000.6.8f1**.
- Current checked-in scene is `Assets/Scenes/SampleScene.unity`. The Build Settings instead point to `Assets/CityHighways/Scenes/CityHighways.unity`, which is **not committed**.
- The latter is generated by `CityHighwaysBuildTools.SetupProject()` through **City Highways → 1. Настроить проект для сборки**.
- `CityHighwaysApp` creates its `UIDocument` at runtime; `MainMenuView`, `GameView`, and `MapView` build much of the UI through C#.
- `City3DScene.TryCreate` creates a 3D root dynamically based on the `CityMap` model. Editing an arbitrary object in a saved scene **does not** currently modify the generated game map.
- Some large sources: `GameView.cs` ~241 KB, `MapView.cs` ~154 KB, `City3DScene.cs` ~124 KB.
- Existing boundaries `Core/`, `Presentation/`, `Net/`, `Steam/`, `Ugs/`, `Editor/`, `Tests/` already have assembly definitions. Keep these boundaries while refactoring.

## Planned incremental migration

### A. Reliable scene source of truth

1. In Unity, use the existing setup command to generate `Assets/CityHighways/Scenes/CityHighways.unity`.
2. Verify it contains a camera and a single `CityHighwaysApp` entry point, then commit the **scene and its .meta**.
3. Introduce separately editable scenes (bootstrap, menu, gameplay, results) only once navigation lifecycle and startup dependencies are explicitly modeled; never change Build Settings to missing scenes.
4. Add validation of build scene paths so a clean clone can build.

### B. Edit mode authoring vs runtime state

1. Introduce a serialized map-layout asset (starting with a small, non-authoritative visual subset) and an editor preview.
2. Make 3D scene generation consume *optional* authored visual anchors with backwards-compatible fallback to the procedural layout.
3. Use prefabs for repeatable visuals where appropriate. Gameplay state still comes from Core, not Transform positions.
4. Expose authorable values via `[SerializeField]` and ScriptableObjects with validation and defaults; do not change balance as part of the migration.

### C. Folders, dependencies and safe moves

Proposed new asset directories under `Assets/CityHighways/`: `Scenes/`, `Prefabs/`, `Configurations/`, `Art/`, `Audio/`; retain existing `Core/`, `Presentation/`, `Net/`, `Steam/`, `Ugs/`, `Editor/`, `Tests/` unless an asset is deliberately moved.

**Never bulk-move Unity assets with Git alone**: move the asset with its `.meta` (preserve the GUID) and check `Resources.Load` paths, asmdef boundaries, hardcoded `AssetDatabase` paths, build references and tests.

## Acceptance criteria

- Fresh clone has a tracked boot scene, and the listed Build Settings scene exists.
- Artist/designer can move a visible authored object in Scene View and observe the result in Play Mode without editing C#.
- Optional serialized visual settings can be changed in Inspector and survive reload.
- Procedural fallback works for old maps and saves; no change to replay determinism.
- Existing Edit Mode tests and localization checks pass in CI; manual gameplay and narrow-layout tests performed in Unity.

## Suggested commit sequence

1. Architecture audit and scene source-of-truth workflow.
2. Commit generated boot scene with `.meta` (generated **inside Unity**).
3. Add map authoring asset and editor preview, without changing gameplay.
4. Wire map visuals to authoring data, keep runtime fallback.
5. Extract visual prefabs and configurations feature by feature.
6. Split oversized presentation responsibilities only after regression coverage.

**Note:** This audit does not claim that a new scene or prefabs have already been generated or tested inside Unity.
