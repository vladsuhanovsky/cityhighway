### Product goal

Make profile customization visible during actual matches, not merely in menus. A player earns influence/experience, unlocks cosmetic items, customizes a character and company/fleet, and sees those choices reflected in the city. No pay-to-win, gameplay bonuses, changed road ownership rules or new monetization assumptions.

### Architecture and constraints

- Five primary tabs: Overview, Wardrobe, Collection, Achievements, Mastery. Existing Style features move to relevant sections; existing wallet functions must remain reachable. Detailed match history/analytics stay in canonical Statistics screen; profile only shows concise highlights.
- First inspect current profile models, catalog IDs, unlock/purchase logic, save/profile/cloud boundaries, preview render pipeline, Interface Editor, existing match FX and city traffic/vehicle rendering. Reuse existing systems rather than create parallel progression or event buses.
- Separate cosmetic presentation from deterministic Core: consume existing committed action/FX notifications where possible; no changes to game RNG, scores, turn order, ownership, road connectivity, contracts or authoritative state. Cosmetic snapshots are validated and bounded, with safe default for old profiles, unknown/missing assets and offline players. Do not transmit untrusted assets or arbitrary paths. No live Steam/Supabase changes without separate approval. Defer remote cosmetic synchronization until protocol/identity compatibility and privacy are tested.
- Apply cosmetic assets to the actual action owner (not simply the current local profile); local/hotseat/bot/remote fallback behavior explicit. Ensure replay/load/undo/redo, repeated callbacks and game teardown do not create stale/duplicate effects. Observation and visual simulation cannot block gameplay or consume game RNG.
- Bounded pools, LOD, quality settings, reduced motion, no unnecessary physics/pathfinding for decorative agents; measure cold/warm startup, frame P95/P99, memory and object counts against same-map baseline. No unsupported FPS claims.
- The approved mockups are art direction, not actual Unity assets. New rigged models, item renders, animation clips and commercially usable licenses require asset work/validation. Do not represent 2D generated reference art as finished rigged models.
- Retain current profile data, purchases, inventory, achievement progress, user preferences, saves/replays and profile isolation. No removal of existing features without a replacement path. No real-money systems or economy rebalancing in this scope.

## Batch 2 — Character 2.0 foundation and item thumbnails (CI pending)

Batch 1 merged in #146 (3bed5cc): 1,468 Edit Mode tests, Play Mode, Interface Editor and main-menu guard passed, no C# warning lines in final Edit Mode log. Visual acceptance remains open.

Asset audit: the actual customizable profile is a stack of transparent 512×768 Scenario PNG layers, not a rigged mesh. The shipped catalog contains 58 IDs (29 per gender), seven slots, default outfits, three skin tones and authored hide/order/bounds metadata. TurntableCharacter simulates rotation by squeezing/tinting layers. Avatar3D/Avatar3DStage is a separate six-role system with optional model/portrait fallback; those characters are not interchangeable with player wardrobe items. Existing Models3D supplies optional city models and is a separate rendering path. Neither source code nor catalog is evidence of a commercially licensed compatible character skeleton or animation set.

- ProfileAppearance is a cosmetic-only snapshot from existing Outfit/PlayerLook. It resolves known IDs using the existing parser, limits serialized input to 4096 characters and separates equipped IDs from visible ones without changing stored entitlements. It is not a network authorization mechanism or a new save format.
- ProfileAvatarRig is an optional prefab authoring component. Use a shared skeleton, rig gender (m/f), separate descendant visual variants keyed by the exact existing item IDs (body, hair, hat, top, bottom, shoes, accessory). Keep skeleton/bones outside switchable variant roots. Bind skinned meshes or socket objects as appropriate. Invalid/duplicate/external/nested bindings are rejected; unsupported visible IDs leave previous instance unchanged. Hidden variants stay inactive. The custom Inspector lists missing catalog IDs and previews a default outfit on a scene instance with Undo. No rig asset or actual 3D runtime preview has been supplied yet. Do not instantiate arbitrary user-supplied paths. Skin fit, material variants, hair clipping, animation/LOD and commercial rights require real asset validation; current 2D hair masking and layer order are not physical mesh collision handling.
- WardrobeItemPreview now uses the existing isolated layer with catalog bounds, clamped and fitted inside a fixed thumbnail without creating textures or reading back pixels. All tiles reserve equal preview/name/rarity space and use full-width action buttons. Existing click, try-on, drag, purchase, outfit and gender behavior preserved. Body thumbnails naturally show the body; some legacy art layers contain exposed skin. Missing art displays a placeholder, not an invented render.
- Fourteen new Edit Mode cases cover all catalog IDs, hidden items, unknown/oversized data, rig selection and rejection, and crop bounds. Tests use synthetic GameObjects, not actual imported character models. No new assets or ownership/economy changes.

Next: visual acceptance of item cards in RU/EN; actual compatible modular mesh/rig and animation acquisition or authoring, isolated 3D profile preview with legacy fallback and lifecycle checks. Only then use the same outfit identity in city agents. Existing role abilities and default renderer remain unchanged. User approval of mockups is not a license for a third-party model.
